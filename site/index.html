llm-serve

A from-scratch GPT-2 inference server on CPU. The model is a fixed workload; the subject is the scheduler and the KV cache memory manager.

At 4 requests/second, continuous batching with a paged KV cache served 3.70 req/s within the latency SLO, against 0.57 for static batching and 0.07 for the naive server. Its best goodput anywhere on the sweep was 3.70 req/s. Medians of 3 seeds; ranges are shown in the tables.

This is CPU-only. Absolute numbers are far below any GPU system, and batching gains are smaller than GPU literature reports, because a CPU hits its compute limit before its memory-bandwidth limit. The limitations are listed in full below.

Behaviour under load

Past saturation

Up to 4 req/s the full system keeps p99 TTFT at 0.21 s. At 8 req/s (about twice its capacity) p99 TTFT rises to 12.3 s, so latency does degrade sharply past saturation. It stays bounded rather than growing without limit because the queue cap of 64 refuses excess work with HTTP 429: a median of 25 requests per run were rejected while 199 completed. Nothing crashed. No request was left unfinished at the cutoff.

Sweeps

Long-prefill stall

One 800-token prompt arrives at t=15 s into steady 2 req/s load. Prefill is not chunked, so every running request waits for it. The largest gap between two tokens seen by ordinary requests was 95 ms without the long prompt and 332 ms with it (median of 3 seeds). It is one stall of a few hundred milliseconds, visible as a single outlier rather than a shift in the whole distribution.

Methodology

  • Arrivals: open-loop Poisson from a Go load generator (bench/); TTFT is measured from the scheduled arrival, so generator lateness cannot hide server latency.
  • Window: 30 s of arrivals plus 20 s of drain; requests unfinished at the cutoff count as failures. 171 runs in total. Fewer requests per data point (about 60-90) than the methodology document's "few hundred": each configuration is instead repeated with 3 seeds (ablation and load curves) or 2 seeds (sweeps).
  • SLO: p99 TTFT under 2 s and p99 TPOT under 200 ms (per-request thresholds for goodput), chosen before measuring.
  • Warmup: 3 sequential requests, discarded, then server counters reset.
  • Admission control: every variant runs with the same queue cap of 64 requests.
  • Threads: torch threads pinned to 4 for every variant.
  • Correctness: every configuration passes the golden test: greedy token IDs identical to the HuggingFace reference, including batches where neighbours join and leave mid-generation and requests that are preempted and recomputed.
  • Static baseline is generous: finished rows leave the compute (a naive server would keep computing them) and tokens stream as produced. Continuous batching's gain over it is therefore conservative.

Limitations

  • CPU only, fp32. Absolute numbers are far below any GPU system, and batching gains are smaller than GPU papers report because the CPU runs out of compute before memory bandwidth.
  • Paged attention gathers blocks into a temporary buffer instead of using a fused kernel, so paging has a real cost on this implementation that a production system would not pay.
  • Batches are padded, not ragged; padded attention width is wasted compute (measured in the milestone logs).
  • GPT-2 only: no grouped-query attention, no RoPE, no quantisation.
  • Prefill is not chunked, so a long prompt stalls the decode loop (chart above).
  • Preemption recomputes instead of swapping to host memory.
  • Single process, single machine. The HTTP layer, the Go generator and the engine share one CPU.
  • Workload lengths are scaled down about 3x; runs are shorter than a production benchmark.

Every # LIMITATION: comment in the code

  • cache.py: attention needs K/V that live in scattered blocks. vLLM's PagedAttention is a fused CUDA kernel that walks the block table inside the attention computation. We cannot write that here, so every layer of every step copies the needed blocks into a temporary contiguous buffer and runs ordinary attention on the copy. Correct, but it moves roughly the whole KV cache through memory once per token.
  • scheduler.py: a long prefill blocks the decode loop for every running request. Production systems chunk the prefill and interleave it with decode steps.
  • scheduler.py: contiguous slots each reserve the full 1024-token context up front.
