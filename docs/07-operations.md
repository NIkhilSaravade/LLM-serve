# 07 — Operating llm-serve

This is the on-call view of the project: what to watch, what "healthy" means, what to do when
it is not, and how changes reach production. Everything measured here comes from the benchmark
in `docs/06-build-log.md` (M6); anything not verified is listed at the end.

## What runs

One process per replica: FastAPI + a scheduler thread that owns the model (GPT-2 small, fp32)
and a fixed KV-cache pool. **One uvicorn worker per container**: a second worker would load a
second model and a second pool. Scale by replicas.

| Endpoint | Purpose |
|---|---|
| `GET /health` | liveness: process up and scheduler thread alive (503 if the thread died) |
| `GET /ready` | readiness: model loaded and warmed up |
| `GET /metrics` | Prometheus exposition |
| `GET /version` | git sha, model, torch version, effective engine config |
| `POST /generate` | inference; `stream=true` returns NDJSON, one line per token |
| `GET /stats`, `POST /stats/reset` | JSON summary used only by the benchmark harness |

Every request carries an `X-Request-ID` (accepted from the caller or generated), echoed in the
response and written to a structured JSON log line when the request finishes.

## SLIs and SLOs

| SLI | Definition | SLO | Why this number |
|---|---|---|---|
| Time to first token | arrival to first token | 99% of requests under 2 s | what a user feels as "did it hang"; same threshold the benchmark used |
| Time per output token | mean gap after the first token | p99 under 200 ms | reading speed |
| Admission | share of requests answered 429 | under 5% | sustained rejection means under-provisioned, not "working as designed" |
| Availability | scrape target up and scheduler thread alive | 99.9% | |

HTTP 429 is deliberate load shedding, so it is excluded from the latency SLIs and tracked by its
own SLI instead. The SLOs were chosen before the benchmark was run (`docs/04`), not fitted to it.

**Error budget.** A 99% TTFT SLO leaves a 1% budget. `LLMTTFTSLOFastBurn` pages when the budget
burns 14.4x too fast over both 1 h and 5 m (about 2% of a 30-day budget in an hour); the
`LLMTTFTp99High` warning catches slower degradation.

## Dashboards and alerts

Grafana dashboard `llm-serve` (generated by `scripts/build_dashboard.py`, provisioned by
`deploy/docker-compose.yml`): SLO attainment, rejection ratio, queue depth vs cap, KV in use,
requests by outcome, TTFT/TPOT/E2E percentiles, throughput, queue vs running batch, KV token
efficiency, preemption rate.

Alerts live in `deploy/prometheus/alerts.yml` (the Kubernetes `PrometheusRule` is generated from
it). Tests check that every metric a panel or alert queries is really exposed by the server, that
every alert has a severity, a summary and a runbook anchor below, and that the generated files
are not stale.

| Alert | Severity | Meaning |
|---|---|---|
| LLMServeDown | critical | target not scrapable for 2 m |
| LLMSchedulerThreadDead | critical | process up, scheduler thread dead: serving nothing |
| LLMTTFTSLOFastBurn | page | error budget burning at 14.4x |
| LLMTTFTp99High / LLMTPOTp99High | warning | latency above SLO for 5 m |
| LLMHighRejectionRate | warning | over 5% of requests rejected |
| LLMQueueNearCap | warning | queue above 75% of its cap |
| LLMKVMemoryPressure | warning | KV above 95% for 10 m |
| LLMPreemptionStorm | warning | evictions above 0.5/s |

## Capacity planning

Measured on one i7-14700K with 4 torch threads per replica, workload B (scaled-down, see
`site/index.html`), continuous batching + paged KV:

- **Goodput peaks at about 3.7 requests/s per replica** (offered 4 req/s); throughput 175-285
  tokens/s depending on batch size (the max-batch sweep flattens above 8 rows: the CPU is
  compute-bound).
- Past that point p99 TTFT climbs (12 s at 8 req/s offered) until the queue cap starts returning 429.
- **Plan for 60-70% of peak per replica**: about 2.5 req/s of this workload. Replicas needed =
  `ceil(peak_offered_rps / 2.5)` plus one for a rolling update or a node loss (`maxUnavailable: 0`
  and a PodDisruptionBudget keep capacity through both).
- Your prompts and outputs are longer than the benchmark's, so **re-measure with your own length
  distribution** (`bench/`) before trusting these numbers.

Memory per pod: model and runtime about 0.9 GiB + KV pool (`kv_budget_mib`). The pool is zero-filled
at start, so it is resident immediately. Measured in the container: RSS 1.95 GiB with the default 1 GiB
pool. The pod limit is 4 GiB, and a unit test enforces `kv_budget + 1.5 GiB <= limit` (a conservative
margin over the measured 0.9 GiB).

The image is 2.75 GB, dominated by PyTorch and transformers. Start-up to ready is about 6 s from a
warm image because the weights are baked in; a cold node adds the image pull.

## Autoscaling

The shipped HPA scales on CPU (65%). That works because decode is CPU-bound, but it lags: CPU
saturates only after the queue has already grown. The better signal is queue depth. With KEDA:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: llm-serve, namespace: llm-serve}
spec:
  scaleTargetRef: {name: llm-serve}
  minReplicaCount: 2
  maxReplicaCount: 8
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring:9090
        query: avg(llm_queue_depth{namespace="llm-serve"})
        threshold: "8"          # scale out when the average queue passes 8 (cap is 64)
```

Scale-down is slow on purpose (10-minute stabilization): a new replica needs about 30 s to load and
warm up, so flapping costs more than idle capacity.

## Release, rollout and rollback

1. **CI gate** (`.github/workflows/ci.yml`): golden tests (greedy tokens identical to the
   HuggingFace reference, including batching, eviction and recompute), API/metrics tests, deploy
   config tests, Go vet/build, and a container smoke test. A change that alters model output cannot
   merge.
2. **Image = model version.** The GPT-2 weights are baked in at build time and the runtime is
   offline (`HF_HUB_OFFLINE=1`). Tag with the git sha (never `latest`); `GET /version` reports it.
3. **Rollout:** rolling update, `maxSurge: 1`, `maxUnavailable: 0`; a new pod receives traffic only
   after `/ready` (model warmed). `preStop` sleeps 10 s so the pod leaves the Service before
   SIGTERM, then uvicorn stops accepting and lets in-flight generations finish within
   `terminationGracePeriodSeconds: 90`.
4. **Canary:** run a second Deployment with one replica of the new tag behind the same Service
   selector label (`track: canary`), compare its TTFT/TPOT histograms against stable for an hour,
   then promote. (Not automated here.)
5. **Rollback:** `kubectl rollout undo deployment/llm-serve -n llm-serve`; five revisions are kept.
   Config-only changes (`configmap.yaml`) also need a rollout because the KV pool is sized at start.

Model changes (a different checkpoint) are a new image tag and a new set of golden fixtures
(`scripts/make_fixtures.py`, committed and reviewed as a diff). There is no model registry: with
one small model baked into the image, a registry would be ceremony.

## Runbooks

<a id="runbook-llmservedown"></a>
### Runbook: LLMServeDown

1. `kubectl -n llm-serve get pods -l app=llm-serve` and `kubectl describe pod`: look for
   `OOMKilled` (raise the memory limit or lower `kv_budget_mib`), `CrashLoopBackOff`, or pods
   stuck not-ready.
2. `kubectl logs <pod> --previous`: startup failures print before the `"event": "ready"` line.
3. If the image is fresh, `kubectl rollout undo`. If every replica is down, check the node, not
   the app.

<a id="runbook-llmschedulerthreaddead"></a>
### Runbook: LLMSchedulerThreadDead

The scheduler thread crashed with an unhandled exception; the API is up but nothing progresses.
Liveness (`/health`) returns 503 and the pod is restarted automatically. After the restart, read
`kubectl logs <pod> --previous` for the traceback and file a bug: this is never expected. If the
restart loops, roll back.

<a id="runbook-latency"></a>
### Runbook: high latency (TTFT / TPOT / fast burn)

1. Dashboard: is `llm_queue_depth` growing? If yes it is overload, go to the overload runbook.
2. Queue empty but TPOT high: the batch is too big for the CPU (`llm_running_requests` near
   `max_batch`) or the node is contended (CPU throttling in `container_cpu_cfs_throttled_*`).
   Threads must equal the CPU limit; extra threads make tail latency worse.
3. One large TTFT spike with an otherwise flat line is a long prompt: prefill is not chunked, so
   an 800-token prompt stalled every running request for about 330 ms in the benchmark. Known
   limitation; a per-request prompt-length cap at the ingress bounds it.
4. Compare replicas: one slow replica points at its node, not the code.

<a id="runbook-overload"></a>
### Runbook: overload (rejections, queue near cap)

Offered load exceeds capacity: `sum(rate(llm_requests_total[1m]))` against replicas x 2.5 req/s
(see Capacity planning). Add replicas (`kubectl scale`, or raise the HPA `maxReplicas`). Rejections
(429 with `Retry-After: 1`) are the system protecting latency; do NOT raise `max_queue` to make the
alert stop, because a deeper queue only moves the failure to a latency SLO breach.

<a id="runbook-kv-memory"></a>
### Runbook: KV memory pressure / preemption storm

`llm_kv_units_used / llm_kv_units_total` above 95% means concurrency is memory-bound; each eviction
throws away work and recomputes it later. Options in order: raise `kv_budget_mib` (and the pod
memory limit with it), lower `max_batch`, or add replicas. If `llm_kv_token_efficiency` is low with
paged KV, blocks are too large for the request mix: try `block_size` 8 (see the block-size sweep).

## Failure modes

| Failure | Behaviour |
|---|---|
| Client disconnects mid-stream | request is cancelled, its KV blocks are freed, no compute wasted |
| Queue full | HTTP 429 + `Retry-After: 1`, counted in `llm_requests_total{status="rejected"}` |
| Request larger than the whole KV pool | HTTP 413 (otherwise it would be evicted and readmitted forever) |
| KV pool exhausted mid-decode | most recently admitted request (among the least-preempted) is evicted and recomputed; tokens stay exact |
| Replica killed | in-flight streams on it are lost (clients must retry); other replicas unaffected |
| Slow/hung model | no per-request deadline in the engine: enforce one at the ingress |

## Security posture

Non-root user (uid 10001), read-only root filesystem, all capabilities dropped, no privilege
escalation, `RuntimeDefault` seccomp, restricted pod-security namespace label, offline weights (no
egress needed at runtime), no secrets in the image or manifests. **There is no authentication or
rate limiting per client**: put the service behind an ingress/gateway that provides both.

## What has been verified, and what has not

Verified on the development machine (Windows, Docker Desktop):

- **The image builds and serves.** Run with the same restrictions as the pod (`--read-only`, tmpfs
  `/tmp`, `--cap-drop ALL`, `no-new-privileges`, non-root uid 10001, 4 CPUs, 4 GiB): ready in about
  6 s with no network access, the Docker healthcheck passes, and `POST /generate` returns exactly
  the token ids of the golden fixture (`[262, 3139, 286, 262, 4141, ...]`).
- **The compose stack works end to end.** Prometheus scrapes the server, all 12 rules load and are
  healthy, Grafana provisions the datasource and the 13-panel dashboard, and under a real 2 req/s run
  from the Go load generator every one of the 19 dashboard queries returned data.
- **`promtool check rules` accepts the alert rules** (12 rules).
- **No alert fired during a healthy run.**
- **Observability overhead is not measurable.** A/B on the same machine in the same session, same
  config and seed (paged + preemption, workload B, 4 req/s): previous commit 0.83 req/s goodput,
  current code 0.90 req/s. The machine itself was about 2x slower at that moment than during the
  published benchmark session (the stored run of that config and seed had 224.8 tok/s and TPOT p99
  52 ms; both versions now measure about 107 tok/s and about 140 ms). Published numbers were not
  re-collected, and absolute figures on a desktop drift between sessions: compare configurations
  within a session, as the benchmark does, never across days.

Not verified:

- **The Kubernetes manifests have not been applied to a real cluster.** They render with
  `kubectl kustomize`, unit tests check their internal consistency, and the container was run under
  the equivalent security restrictions, but probes, the HPA, the PodDisruptionBudget, the
  `preStop` drain and the Prometheus Operator resources are untested against a live API server.
- **No alert has been seen firing.** Expressions parse and evaluate; thresholds are reasoned from the
  benchmark, not tuned on production traffic. A multi-window burn-rate alert in particular needs an
  hour of bad traffic to exercise.
- **The GitHub Actions workflow has never run** (this repository has no remote yet). Each step was
  run locally by hand, except the `kubectl` and container steps, which were run as described above.
- `llm_preemptions_total` and `llm_decode_steps_total` are read from the engine's own counters, which
  the benchmark's `POST /stats/reset` zeroes: never call it against a production replica.
- No multi-replica load balancing beyond kube-proxy, no authentication, no tracing, no canary
  automation, no GPU support.
